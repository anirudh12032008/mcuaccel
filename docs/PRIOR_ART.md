| Jacob et al., "Quantization and Training of Neural Networks for Efficient Integer-Arithmetic-Only Inference", arXiv 1712.05877, doi 10.48550/arXiv.1712.05877 (`jacob2018quantization`) | Affine uint8 quantization `real = S(q - Z)`; the layer rescale `M = S1 S2 / S3` is written as `M = 2^-n M0`, `M0` in [0.5, 1), applied as a 32-bit fixed-point multiply by `M0` plus a rounding right shift, after an int32 accumulate with bias merged in **[pdf]**. ## 3. The two in-house dependencies (read from disk)

### 3a. corv32 (`corv32_repo`), `/Users/anirudh/corv32`, commit e1d0bc0 (vendored subset in this repo)

- What it is: a from-scratch five-stage in-order RV32IM core with M-mode traps/interrupts and a small SoC (boot ROM, RAM, CLINT, UART, GPIO, SPI-flash boot) (`docs/SPEC.md` section 1). PicoRV32 and VexRiscv are used only as measured baselines.
- Status at the commit used here: PLAN.md lists only the walking skeleton (`corv32_sc`, executing LUI/ADDI/SW/JAL) as done and M1-M7 open; no FPGA board is attached in its environment (`docs/ENVIRONMENT.md`). This is why `docs/DECISIONS.md` D1 substitutes PicoRV32 as the host CPU. No core-level performance number exists yet; DESIGN 7.8 CPI figures are labelled predictions. DESIGN section 11 budgets corv32 core at <= 2,500 LUT4, Fmax >= 75 MHz on LFE5U-25F-6.
- Bus we must speak (`docs/DESIGN.md` section 3): OBI-style `req/gnt` address phase plus `rvalid` response, at most one outstanding request per bus, word-aligned addresses, `be[3:0]` byte enables on dbus; a zero-wait synchronous BRAM slave gives `gnt=1` and `rvalid <= req`, i.e. one 32-bit access per cycle with one-cycle latency. Memory map section 8.1: RAM at 0x8000_0000 (64 KiB on FPGA). That single 32-bit port, one word per cycle, is the bandwidth roof every model in this project is measured against.

### 3b. mcugrad (`mcugrad_repo`), submodule at e9f6283

- What it is: stdlib-only autograd framework plus an AOT compiler: graph IR, int8 post-training quantization, bit-exact Python simulator (`mcugrad.quant.sim.run_int8`, `int8ops`) and a C99 emitter that produces one self-contained file with a static arena, no malloc/libm (`README.md`; `mcugrad/quant/QUANT.md`).
- Quantization scheme (`QUANT.md`): activations int8 per-tensor asymmetric; weights int8 per-output-channel symmetric (range -127..127); int32 bias; per-channel requant `(mult,shift)` from `x_scale*w_scale_c/y_scale`; `y = clamp(requant(acc) + y_zp, act_min, act_max)`; relu fused as `act_min = y_zp`. Requant is `RDBPOT(SRDHM(acc << ls, mult), rs)` (`mcugrad/codegen/kernels/mg_int8.h`, functions `mg_srdhm`, `mg_requant`). Kernels present: `mg_conv2d_nhwc_s8`, `mg_conv1x1_nhwc_s8`, `mg_dwconv2d_nhwc_s8`, `mg_fc_s8`, plus max/avg pool, add, affine, softmax (LUT), pad and transpose. These last are the layers that stay in software in our design and set the Amdahl floor (section 4).
- Measured accuracy (`third_party/mcugrad/results/quant.csv`, 512 calibration images): mnist_cnn fp32 98.70%, int8 per-channel 98.69%, per-tensor 98.71% on 10,000 test images; cifar_mobilenet (38,602 params) fp32 83.34%, int8 per-channel 83.08%, per-tensor 83.21% (README states n=1,000 CIFAR images for that run).
- Bit-exactness already shown: generated C vs simulator 0/1,000 mismatches on both models, 0/200 on random-init MobileNet, fuzzer 1,000 random CNNs with 0 mismatching bytes of 201,104 (README, `results/host_bitexact.csv`, `results/notes/fuzz_codegen.md`); mcugrad vs TFLM host build 0 differing logits (`results/MILESTONE_8.md`).
- **Per-inference cycle counts on RP2040 / ESP32-S3: none exist.** `third_party/mcugrad/results/device.csv` has `PENDING DEVICE` in `cycles_median`, `us_median`, `n`, `acc`, `clock_hz` for every row (README: "No RP2040 or ESP32-S3 is attached to the measurement machine"). The only device numbers are static sizes (e.g. mnist_cnn rp2040 flash 838,112 B, static RAM 23,880 B; arena 7,840 B mnist, 20,480 B cifar_mobilenet).
- What does exist is emulated retired-instruction counts, not cycles (`results/emulated.csv`, QEMU 11.1.1 ARMv6-M microbit model and Espressif QEMU 9.2.2 Xtensa LX7; `results/notes/emulation.md`: "not device latency, not cycles"): per image, ARMv6-M mcugrad mnist_cnn 2,732,632 instructions and cifar_mobilenet 16,101,414; TFLM reference kernels 9,951,694 and 49,151,339 (3.64x and 3.05x more). Xtensa LX7 (`insn = 25 x CCOUNT @ icount0`, an inferred unit): mcugrad 2,889,975 and 19,031,475; TFLM 24,290,625 and 142,616,525. Accuracy on the emulated subsets: 98.2% (1,000 images) and 83.25% (400 images), logits identical to the host in all runs.
- Consequence for us: the software baseline's cycle counts on RISC-V must be measured by us on PicoRV32 with `rdcycle` (D6). The ARM instruction counts above are only a scale hint, not a prediction (RISC-V instruction counts and PicoRV32's CPI of about 4, section 4, differ). Back-of-envelope only, not a result: 16.1 M instructions at CPI about 4 is on the order of 60 M cycles for cifar_mobilenet.

## 5. Memory-mapped coprocessor vs ISA extension on microcontroller-class RISC-V

| Source | What it shows |
|---|---|
| XpulpNN, PULP-NN (`garofalo2020xpulpnn`, `garofalo2019pulpnn`) | In-pipeline SIMD dot-product and MAC-and-load instructions, hardware loops; no bus transaction per MAC; scales by adding cores. Cost: change to the core, compiler support, register-file pressure (4x2 MatMul fits RI5CY's registers; a 4x4 layout does not, per the XpulpNN text) **[pdf]**. |
| CFU Playground (`prakash2023cfu`) | Custom-instruction (R-type) interface to VexRiscv, used to grow a unit "until it almost becomes a full-blown ML accelerator" **[pdf]**; fine-grained, CPU stays in the loop moving data (about 2 cycles per MAC at one stage, below 1 cycle per MAC only after the whole inner loop moved into the CFU **[pdf]**). |
| CV-X-IF (`cvxif`) | OpenHW standard to attach coprocessors to CV32E40X-class cores without modifying the pipeline/decoder; replaces the tightly pipeline-coupled APU interface of CV32E40P **[abs]**. The page opened does not describe the channels. |
| Rocket Chip (`asanovic2016rocket`) / Gemmini | Accelerators attach as ISA extensions, coprocessors (RoCC) or standalone cores **[abs]**. Gemmini uses RoCC commands from Rocket and accesses memory via its own TLB/L2 path **[pdf]**. |
| PicoRV32 PCPI (`picorv32`) | The core offers a PCPI interface that hands unrecognised instructions to an external coprocessor, with a 16-cycle ack timeout **[abs]**; MUL takes 40 cycles, MULH 72 cycles with `ENABLE_MUL`, `ENABLE_FAST_MUL` gives a single-cycle multiplier (cycle count not stated); average CPI about 4 (Dhrystone CPI 4.1 at 0.516 DMIPS/MHz); no CoreMark number **[abs]**. |
| ECP5 (`lattice_ecp5`) | LFE5U-85: 84K LUTs, 156 18x18 multipliers, 3,744 Kb in 208 sysMEM blocks of 18 Kb, 669 Kb distributed RAM **[abs]**. This is the budget envelope; the page lists "84K" while "85F" part-number links point at the SERDES variant, so the final LUT/DSP budget must cite the datasheet that was opened for synthesis (not done here). |

Trade-off reading. Memory-mapped (our choice): no core change, any core works (the claim is about the same core in both runs), accelerator masters the bus itself and removes the CPU from the data path; cost: configuration and completion traffic over the same single 32-bit port, plus polling. ISA extension: no setup overhead, but needs core and compiler changes and is limited by register-file operand bandwidth. The "same core" comparison we run is valid for either, but a reviewer may reasonably ask for a SIMD-dot-product-in-software baseline (what PULP-NN does) to show how much of the 10x is just "any int8 SIMD".

## 6. What prior art settles and what remains open

### Settled (be blunt)

1. A dedicated int8 accelerator beating a scalar in-order RISC-V core by at least 10x on CNN kernels is already well established, many times, and by large margins:
   - Gemmini: 2,670x (ResNet50, in-order Rocket), 127x (MobileNetV2) at 1 GHz, whole-network, ASIC simulation (`genc2021gemmini`).
   - CFU Playground: 55x on MobileNetV2's dominant 1x1 conv operator on VexRiscv/Arty (`prakash2023cfu`), and 75x on KWS on Fomu of which 3x was the CFU and 25x came from CPU, memory and software changes.
   - Yildirim and Ozturk: up to 59.3x on depthwise-separable blocks vs software on a RISC-V core (`yildirim2025dsc`, preprint).
   - PULP-NN: 63x vs one RV32IMC core, but with 8 cores and SIMD, so not accelerator-only (`garofalo2019pulpnn`).
   - TPU-class results 15-30x vs a server CPU (`jouppi2017tpu`) are a different regime.
   So "the accelerator is >=10x faster than software on the same scalar core" is not a contribution on its own. Counter-signal worth remembering: VTA on edge FPGAs only reaches 2-12x over an ARM core (`moreau2018vta`), and CFU's whole-network 75x was 3x from the CFU.
2. Bit-exact int8 arithmetic in the gemmlowp/TFLite style, with SRDHM+RDBPOT in hardware, is the standard integer pipeline (`jacob2018quantization`, `gemmlowp_fixedpoint`); CFU Playground even puts the post-processing (saturating multiplication, rounding division, clamping) into the CFU for a measured gain (that step 14x faster; cumulative 31.1x on MobileNetV2/Arty including post-processing, 37.64x on KWS/Fomu) (`prakash2023cfu`). Bit-exactness with a software reference is routine at operator level.
3. Bandwidth-driven analytic modelling of FPGA CNN accelerators, validated against an implementation, is also established: `zhang2015optimizing` (roofline-driven DSE, built at 61.62 GFLOPS), `alwani2016fused` (analytic model plus prototype), and the roofline model itself (`williams2009roofline`). Output-stationary vs weight-stationary vs row-stationary taxonomy is textbook (`chen2016eyeriss`, `sze2017efficient`).
4. Amdahl-type effects exist in the literature as observations: `qiu2016going` (conv 187.8 vs whole network 137.0 GOP/s), `genc2021gemmini` (MobileNet depthwise), `prakash2023cfu` (operator vs system speedup), `lai2018cmsisnn` (pooling a small share).

### Not settled, and what would be a defensible contribution

(i) Pre-registered prediction vs measurement. Zhang and Alwani built models and prototypes, but I found no work that freezes (hashes) a bandwidth model before any RTL exists, states its error tolerance in advance, and then reports the measured error including where it fails. The contribution is the protocol and the residuals, not "a model exists". Do not claim novelty for the model itself.

(ii) Bit-exactness with a specific compiler's integer simulator at whole-network level including fallback layers. Neutron Runner does a proprietary version; CFU Playground checks against its own software path; TensorLift proves arithmetic cores. None combines an independently fuzzed integer simulator (mcugrad: 1,000 random CNNs, 0 byte mismatches), a C emitter, and a hardware path with software-fallback layers in the same network, with 0 mismatches per image on the full test set.

(iii) The parallelism-vs-32-bit-bus saturation curve for a microcontroller-class memory system. Published scaling studies are at much larger memory systems (Gemmini 256 KB scratchpad, 1 MB L2; NVDLA 512 KB CBUF; TPU 28 MiB). I did not find a measured MAC-array-width sweep against a single 32-bit, one-word-per-cycle BRAM port with the CPU also sharing that port. The knee of that curve (width at which extra MACs stop helping) and its agreement with a roofline with a 4 B/cycle roof is open.

(iv) Amdahl effects of non-accelerated layers (pooling, add, softmax, pad, transpose, driver overhead) as a measured whole-network decomposition on an MCU-class SoC. Operator-level and whole-network numbers are both reported in the literature, but not the residual-layer share as a function of accelerator width for these networks.

Risks to the 10x itself (from the evidence above): depthwise layers have low reuse (Gemmini: 127x MobileNetV2 vs 2,670x ResNet50; CFU Playground: depthwise was the second runtime contributor and, on Fomu, no resources were left for separate depthwise gateware so the 4-way MAC was reused), so cifar_mobilenet is where the 10x is least safe on a 32-bit port; and the software baseline's speed depends on the PicoRV32 multiplier setting (MULH, needed for SRDHM, costs 72 cycles with `ENABLE_MUL` vs a single-cycle core with `ENABLE_FAST_MUL`), which changes the denominator by a large factor. The baseline configuration must therefore be fixed and published before measurement.

## 7. Recommendation: the sharpest falsifiable claim

Claim (proposed thresholds, to be frozen in docs/SPEC.md before RTL): On the PicoRV32 SoC with one 32-bit single-port BRAM and the pinned mcugrad int8 graphs mnist_cnn and cifar_mobilenet, the accelerator at the chosen array width runs whole-network inference, measured with `rdcycle` from model_run entry to exit and including all software-fallback layers and driver/command overhead, in at most 1/10 of the cycles of mcugrad's emitted C99 compiled `-O2 -march=rv32im` on the same core with `ENABLE_FAST_MUL` and the same clock, with every int8 logit byte-identical to `mcugrad.quant.sim.run_int8` on every image of the test set, within the stated LUT/DSP budget on LFE5U-85F; and a Python bandwidth model committed before any RTL (commit hash recorded) predicts the measured accelerator cycles within +/-20% for every array width in the ablation sweep and predicts the width at which speedup saturates to within a factor of two. The claim is refuted by any one of the following observations: whole-network speedup below 10x on either model (the likeliest refutation is cifar_mobilenet, where depthwise layers and unaccelerated pool/add/transpose layers cap the gain by Amdahl's law, and the report must then give the measured non-accelerated cycle share); any logit mismatch against run_int8 on any image; a fitted design above the LUT or DSP budget; any |predicted - measured| / measured above 20% at any width in the sweep; or a measured saturation width outside a factor of two of the prediction. If the model misses, the paper reports the residuals and the cause, which is itself the contribution; it must not retune the model after seeing measurements and call that a prediction.
